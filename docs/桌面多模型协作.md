> 服务商配置要改改，一次可以配置多个服务商，能自定义配置，每个服务商能配置多个 ai

> 该服务商里的所有 ai 大模型，选择一个 ai 大模型可以在对话里面沟通，ai 大模型可以选择
> 思考强度和上下文文本大小，可以参考 zcode 的配置

| 问题 | 用户选择 | 影响 |
|---|---|---|
| 思考强度/上下文放哪 | **跟着模型走** | 不用全局值，每个 `provider+model` 记自己那一对 |
| 模型列表从哪来 | **界面手动增删** | 不联网发现、不依赖 Key |

## 1. 数据形状换了

`ProviderSection.model: str` → `models: tuple[ModelSpec, ...]` + `default_model: str`。

为什么不是一张平铺的 `(provider, model)` 表：**一个 key 属于一个服务商，一个服务商提供若干
模型**。平铺表会让每一行重复服务商名，读者最后还是得在页面上分组——而"分组"正是这一轮要
在界面上做的那两个下拉框。

`ModelSpec` 允许裸字符串或 `{id, label}`：

```yaml
models:
  - deepseek-chat                      # 显示名回落到 id
  - {id: deepseek-reasoner, label: DeepSeek R1}
default_model: deepseek-chat
```

`model` 保留为 property（返回 `default_model`），老调用方一行不用改。

**校验**（都在 `ProviderSection.from_mapping`）：清单非空、id 不重复、`default_model`
必须在清单里；`default_model` 留空则取第一个 id。

## 2. 旧配置是硬失败，报错就是迁移说明

```
invalid configuration at 'llm.providers.deepseek.model':
  renamed: list model names under 'models' and pick the starting one with 'default_model'
```

自动升级被否掉了，理由：两种拼法并存之后，每一个读配置的地方都得回答"哪个赢"，而
**"猜哪个赢"正是下拉框和设置面板显示不同模型集合的老路**（§11e 记过一次同类缺陷）。

`jarvis/config/defaults.yaml` 里四个服务商已经改好，照抄即可。用户自己那份
`JARVIS_HOME/config/config.yaml` 已按 1:1 迁移（原文件备份为
`config.yaml.bak-before-multi-model`）。

**偏好表是另一套规则**：`llm.overrides` / `llm.extras` 是本程序写的，不是人手写的，
所以老的单 `model` 字段在那里被**静默迁移**（`_parse_models(..., fallback=...)`）。
两处不同的严格程度是故意的：config.yaml 是人会打开编辑的文件，preferences.json 不是。

## 3. 对话标题栏：两个下拉 + 两个旋钮

```
[服务商 ▾] [模型 ▾] [思考强度 ▾] [上下文轮数 ▾]
```

**选中服务商但没选模型**时落到**该服务商自己的 `default_model`**，而不是一个它没有的模型名。
`choose_model(provider, model="")` 就是这个语义——页面永远知道两级，所以一次调用带两级。

**未知模型名回落到 default 而不是抛异常**。过期偏好是常态（手改的文件、上一版的会话），
把标题栏打成空白不是。`model_spec()` 承担这个回落，`ProviderSection` 里没有第二个地方
需要判断它。

## 4. 两个旋钮按 `provider\x00model` 键存

```
llm.tuning = {
  "qwenai\u0000qwen3.8-flash": {"thinking": "high",     "turns": 20},
  "wkapi\u0000gpt-5.6-sol":    {"thinking": "off",      "turns": 4}
}
```

**NUL 分隔符**，因为服务商名和模型 id 都不可能有 NUL。用 `/` 会让 `a/b`+`c` 和 `a`+`b/c`
拼成同一个键。

**思考强度是四级到真实 token 预算的映射**，不是第二套刻度：

| 档位 | 预算 | 界面 |
|---|---|---|
| `off` | 0 | 不思考（不发送思考参数） |
| `low` | 1024 | 轻度思考 |
| `medium` | 4096 | 中度思考（默认） |
| `high` | 16000 | 深度思考 |

同一单位、和回复里报的 `reasoning_tokens` 对得上——这是"这个旋钮不是装饰"唯一能自证的方式。

**存一个是只写一个**。两个旋钮并排，改一个不能把另一个悄悄复位；`set_tuning` 只写它拿到的
字段，没拿到的沿用当前值。

## 5. 本轮抓到的真缺陷：`llm.tuning` 没进 `PREFERENCE_TYPES`

`Preferences.set()` 对未注册的键是"日志一条 + 返回 False"。于是思考强度和上下文
**每一次写入都被静默拒绝**——下拉框看着能用、level 看着存上了、对话框关掉再开还是新值
（因为读的是默认值），但下一句问答永远用旧的。表现和"功能根本没做"一模一样。

**四道门禁全绿。** 抓到它的是新写的测试，不是门禁。

守卫写在 `tests/test_app_preferences.py`：**枚举模块里所有 `大写 + 含点` 的常量**，要求
它们全部在 `PREFERENCE_TYPES` 里。用枚举而不是手写清单，因为手写清单正是当初出错的那个
东西——它当时也没漏掉自己的检查项。

## 6. 设置面板：每个服务商一张可增删的模型清单

每行显示 `N 个模型 · 起始 X · 来源 · 已改 · key 状态`。编辑区多一块：

- 逐条列出该服务商的模型，带「起始」标记和逐条删除按钮；
- **最后一条删不掉**——后端拒绝（`至少要留一个模型`）**且**按钮置灰，两层都挡；
- 下面两个输入框加模型（id + 可选显示名）。

加/删走**独立的桥面方法**（`llm_add_model` / `llm_remove_model`），不塞进表单保存：
模型清单是个小改动、有自己的回执，并进一次大保存会让一个被拒的模型名看起来像整个表单
失败了。

原来那个"模型名称"输入框改成"起始模型"——它现在只影响"刚切到这个服务商时用哪个"。

### 一个要记住的取舍：窗口里的清单会盖住 config.yaml

`llm.overrides[provider].models` 存的是**整张清单**（配置里的 + 界面加的），不是增量。
理由：**删除必须能表达**。增量只能"加"，删掉一个 config.yaml 里的模型没法表示；而用户要的
就是"界面手动增删"。

代价：在窗口里调过某个服务商的清单之后，**再往 config.yaml 里给它加模型，窗口里不会出现**，
因为整张清单已经被覆盖了。这是 `base_url` 一直以来的同一套语义（窗口改了就盖住文件），
不是新问题。快照里那一行会带 `edited: true` + `source: 配置文件`，所以面板看得出它被改过。
要回到"以文件为准"，把那一行的界面改动清掉即可（`llm.overrides` 里删掉该 provider）。

## 7. 新增/改动的桥面方法

| 方法 | 说明 |
|---|---|
| `chat_models()` | 返回**两级**结构（`providers[]` 各带 `models[]`），不再是 `choices[]` 平铺 |
| `chat_pick(provider, model="")` | 多一个 `model` 参数；返回刷新后的列 |
| `chat_tuning(thinking, turns)` | 新增；两个都可选、互相独立 |
| `llm_add_model(provider, model_id, label)` | 新增 |
| `llm_remove_model(provider, model_id)` | 新增 |

全部遵守既有约定：**对外不抛未包装异常**，设置不可用时返回 `{"ok": False, "error": "设置不可用"}`。
桥面从 79 → **90** 个公开方法。

### 7b. 2026-10-04 又加了几扇（多对话 / 中断 / 圆桌 / 连通测试）

| 方法 | 说明 |
|---|---|
| `chat_send(text, attachments, conversation, provider, model)` | 起一轮就返回 `task_id`，答案走状态快照回来 |
| `chat_cancel(task_id)` / `chat_tasks()` | 停止只对**这一个**任务有效，别的桌子照跑 |
| `chat_conversations()` / `chat_open(id)` / `chat_new()` / `chat_tab_model(...)` | 对话列表、切桌子、开新桌子、这一桌用哪个模型 |
| `chat_round_table(text, seats, rounds, conversation)` | 圆桌：立刻返回 `task_id`；`seats` 是 `{provider, model}` 列表，**顺序就是发言顺序，第一家负责合并** |
| `llm_test(provider, model)` | 「测一下」：两次请求，一次问它能不能答、一次递红方块问颜色 |
| `chat_models()` 的形状变了 | 顶层多一个 `caps[]`（每条是一个 `{provider, model, chat, vision, detail, at}`）；`vision` 用 `null` 表示"没测过"，不等于 `false` |

`llm_add_model` 的语义也变了：**先存后测，连不上原样删回去**（一行还没存在的配置没法探测，
base_url / key 的环境变量名 / 模型 id 全从那行读）。`settings_apply({add_model})` 走同一道门槛。

2026-10-04 实测桥面公开方法 **102** 个（`vars(HudBridge)` 里非下划线可调用项）。这个数字每次
加门都会动，别抄到别处当准数，要就用那条命令现量。

## 8. 手机端跟着改

- `PcModelChoice[]` → `PcProviderChoice[]`（带 `models` / `default_model`）；
- `READ_KEYS['chat_models']`：`['error','current','choices','provider','model','key_set']`
  → `['error','providers','provider','model','models','key_set']`。

手机仍然**不给切模型**，只读地显示"N 个模型 · 起始 X"。`ALLOWED_METHODS` 没有新增
（`llm_add_model` 这类写操作刻意不进白名单——手机不新增能力面）。
`scripts/verify_phone_contract.py` 会按 `READ_KEYS` 核对电脑真的给了这些键。

### 收尾时抓到的第二个真缺口：契约自检自己过期了

`scripts/verify_phone_contract.py` 报 `chat_models 缺 providers, models`，
**看起来像桥面断了，实际是自检里那个手写替身 `_SettingsStub` 还停在一层的
`choices[]` 上**——真服务、手机 `READ_KEYS`、桌面测试都改了，替身没人改。

修法不是"下次记得同步"，而是把不变式写成两层守卫：

- 自检内部：`_real_model_choices_keys()` 用真 `SettingsService` 跑一次，
  拿它的顶层键集和替身比，替身过期当场红灯；
- 常规门禁：`tests/test_mobile_frontend.py` 里用 `HudBridge.__new__` +
  假设置服务拿一次真返回，手机 `READ_KEYS` 声明的键必须都在。
  **反向验证过**：只在 `types.ts` 加一个真桥面不返回的键 → 红灯并点名
  `真桥面没给手机要读的键：['ghost_key']`。

## 10. 没验到 / 不要对外承诺

- **真机点两级下拉的过程**：合成点击点不中 WebView 里的 `<select>` 弹出层（原生下拉，不在
  DOM 里）。逻辑由桥面 11 条单测覆盖，界面层只过了 `vue-tsc` + `vite build`。
- **设置面板新模型清单的实际点击**：同因。
- **端到端**："选到某个模型 → 它按你设的思考强度答了一句"这条**没跑过**，本轮无 API Key。
  验到的是"偏好写对了、客户端按新 provider/model 重建了"——离端到端还差一次真调用。
- 思考强度能不能真的多 think，取决于接的那个端点认不认 `reasoning` 那一套。演示前先拿
  客户的 Key 试一次深度思考，看 `reasoning_tokens` 有没有真的涨。
