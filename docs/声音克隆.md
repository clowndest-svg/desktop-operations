# 声音克隆：两条路，和这台机器上各自的边界

「录一段我的声音，让她用这个声音说话」有两条实现路径，选哪条不是性能调优
问题，是**能不能打电话**的问题。这份文档记录实测数据、各自的失败长相，以及
运维上不能踩的坑。

## 一句话结论

| 路径 | 首块延迟（实测） | 需要什么 | 适用 |
|---|---|---|---|
| **云端**（阿里云百炼复刻 + 实时合成） | 500–1000 ms | DashScope API Key | **手机通话**，唯一可行 |
| **本地**（CosyVoice2 副进程） | 16–19 s | 能装下 3.1 GB 显存的 GPU | 私密、免费、离线；本机已不可行 |

代码入口：`jarvis/tts/cloud.py`（复刻）、`jarvis/tts/cloud_voices.py`（实时合成）、
`jarvis/tts/sidecar.py` + `jarvis/tts/cosyvoice_worker.py`（本地副进程）。
选项逻辑在 `jarvis/app/voice_call.py::_engine_for` 与
`jarvis/app/voice_picker.py::_engine_for_voice`——**两处必须同源**，
否则试听与作答会用不同引擎，这是本功能最费解的一种坏法。

## 为什么本地路径在这台机器上跑不通

两个独立的原因，都会挡住它，且**报错信息都指不到真因**：

### 1. 显存：能报出的空闲量用不上（WDDM）

```
OutOfMemoryError: CUDA out of memory. Tried to allocate 18.00 MiB.
GPU 0 has a total capacity of 4.00 GiB of which 2.06 GiB is free.
Of the allocated memory 1.09 GiB is allocated by PyTorch
```

**2.06 GiB 空闲，却分不出 18 MiB。** 这不是容量不足。实测（`probe_vram.py`）：

- 建完 CUDA 上下文后：free 3288 MiB / 4096 MiB
- `CosyVoice2(...)` 构造中 torch 只占到 1.09 GiB 就 OOM
- 桌面（Chrome、Edge、微信、MuMu 模拟器、WorkBuddy 自身）另外占约 1.2 GB

**`PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` 是标准解法，但 Windows 上
PyTorch 不支持**——它打印一句
`expandable_segments not supported on this platform` 的 UserWarning 之后
**照常继续**，看起来像修好了，实际什么都没发生。这就是为什么
`jarvis/tts/sidecar.py::_child_env` 里**故意不设**这个变量，并写清了理由：
设了会让下一个人以为问题已处理。

另一个观察：**授权工作后错误里的数字会变**（1.83 GiB → 1.51 GiB → 2.06 GiB，
torch 占用 1.31 → 1.60 → 1.09 GiB），随桌面程序波动。也就是说这台机器处在
**临界区**，关掉浏览器有时能过、有时不能，而这不叫"修好了"。

### 2. CPU 兜底：CPU 上也崩

把 GPU 摘掉（`CUDA_VISIBLE_DEVICES=`）再跑，构造阶段以
**退出码 3221225477 = `0xC0000005`（原生访问违例）** 结束，没有 Python 回溯，
stderr 停在 `INFO use wetext frontend` 之后。即"没有 GPU 就退回 CPU"这条路
在这台机器上同样不通——而且它死得比 OOM **更安静**（OOM 至少有异常文本）。

判断"卡了还是崩了"要用退出码：`probe_cpu.py` 里的 `_explain()` 把
Windows 的大负数退出码翻成名称，这是唯一能区分"崩溃"和"加载很慢"的东西。

### 顺带一个坑：`0xC0000005` 的现场怎么读

`jarvis/tts/cosyvoice_worker.py` 有 `XY_WORKER_TRACE` 环境变量：设了就用
stdlib `faulthandler.dump_traceback_later` 周期性把各线程栈打到 stderr。
排查"进程活着、显存不涨、一行输出都没有"这类问题时，它是唯一能分开
「在加载」「死锁了」「根本没收到请求」三者的工具。

## 本地副进程为什么必须存在（以及它跑通过的部分）

CosyVoice 把 `transformers` 钉在 `<4.52`，助手自己的环境是 `5.x`。这是版本
**上限**，懒导入绕不过去，所以只能另起一个进程（`voice-venv`）。

**已在真机验证走通的部分**（`E:\BianChengGongJu\JarvisData\voice-runtime\e2e_sidecar.py`）：

- `voice-venv` 解释器定位、CosyVoice 源码树 PYTHONPATH、缓存重定向——都对
- worker 协议：`load` / `speakers` / `synthesize` / `cancel` / `shutdown` 往返正常
- **模型成功加载过**：31.06 s，fp16，3456 MiB 显存，`builtin_speakers` 正常返回
- 参考音频注册（`add_zero_shot_spk`）与 RIFF 头解析（含 IEEE float 格式 3）都对

**没走完的部分**：加载之后的合成，因为上面第 1/2 条，构造阶段就过不去。

### 一个必须记住的死锁（已修）

worker 里**不能在读 stdin 的线程起来之后才 `import torch`**。实测表：

| 先阻塞读 stdin，再 import | `import torch` |
|---|---|
| 没有该线程 | 9.5 s 完成 |
| `sys.stdin` 迭代 | **永久挂起** |
| `sys.stdin.readline()` | **永久挂起** |
| `os.read(0, ...)` | **永久挂起** |
| 另起线程 `time.sleep(300)` | 9.7 s 完成 |

修法：`_preload()` 在启动 reader 线程**之前**导入 torch + CosyVoice2。
`--no-preload` 保留着，用于在有人怀疑这个结论的机器上重现。
`tests/test_tts_sidecar.py::TestWorkerSourceOrdering` 用**读源码断言顺序**的方式
把这条钉住（不能真的运行它——运行会挂）。

## 云端路径（用户实际选定的方案）

### 为什么是 Qwen 复刻端点，不是 CosyVoice 复刻端点

两个端点都在百炼上，关键差别是**参考音频怎么送**：

- `model: voice-enrollment`（CosyVoice 线）要一个**公网可访问的 URL**。
  手机录音是局域网里的私有文件，没有公网地址——走这条就得先把它传到第三方
  存储并放开读取权限。
- `model: qwen-voice-enrollment`（Qwen 线）接受 **base64 Data URL**，直接发给
  厂商即可。披露面更小，而且对应的合成模型名字就叫 `*-realtime`。

代码里 `jarvis/tts/cloud.py` 的模块 docstring 把这段论证写全了，改端点前先读它。

### 会话是池化的，`close()` 不是断连

`QwenRealtimeVoice.close()` **不关 socket**，只是把会话还回模块级池
（`_POOL`）。原因：调用方 `VoiceCall` 每句都新建引擎再 `close()`，真断连的话
每句都要重做一次 TLS + 会话握手，正好抵消这个模块存在的意义。

- 池键是 `(voice, model, sha256(key)[:12])`——**密钥绝不会进字典键**，
  字典键会出现在 traceback 和调试器里
- `disconnect()` 才真关，并且先发 `session.finish`（让厂商立刻停止计费）
- `shutdown_voice_sessions()` 清空池，注册在 `atexit` 上
- 两个超时：握手 10 s（要快速失败）、流 20 s（要容忍静默）

> **踩过的坑**：`close()` 早期版本会把 `self._ws` 置空再入池，结果
> `disconnect()` 找不到 socket——**池化会话永远关不掉**，每句泄漏一个活连接，
> 直到厂商自己的空闲超时来收。修法是保留 socket 引用，另用 `_pooled` 标志位
> 记录"在池里"。`tests/test_tts_cloud.py::TestRealtimePool` 盯着这件事。

### 忽略 speed / volume 是刻意的

会话握手是这两个参数唯一能放的地方，而握手里有**一个字段不认识就会整会话失败**。
滑块不动，好过通话直接哑掉。本地与 Edge 引擎仍然照常响应这两个参数。

## 录音上传：默认不上传

`voice_clone_add(upload=...)` 默认为 **false**。上传意味着录音离开这台机器、
发到阿里云，这**是一次披露，不是一次性能优化**，所以要明确要求才做。

- 上传**在本地存好之后**才尝试：厂商拒绝时，录音仍在，降级成"本地可用 +
  一句说明"，绝不变成本地也丢了
- 回复里带 `cloud` / `cloud_error`，屏幕能据此告诉用户到底走的是哪条
- 删除音色时，**云端那一半也删**：用户要求删掉录音之后，别人的服务器上还留着
  他的声音克隆，不是这个功能可以停在的状态
- 只在本地音色上，**完全不碰网络**（有测试盯着）

### 上传这段代码为什么必须待在 `app` 层

"上传"其实是**两次调用，且有先后顺序**：先传厂商，再把返回的 id 写回索引；
删除时反过来，先读索引拿到 id，删掉云端，再删本地。这个顺序需要有人负责，
而负责它的地方是 `jarvis/app/voice_cloud.py`——它很薄，只有两个函数。

**踩过的坑**：这段编排最初写在 `jarvis/ui/desktop.py` 里，因为"就两个函数，
不值得新开一个模块"。结果是 `ui -> tts` 出现在导入图上，而 `ALLOWED["ui"]`
只有 `app / config / core`——`test_no_layer_violations` 与
`test_ui_only_talks_to_app_core_and_config` 同时变红。

修法**不是**把 `tts` 加进 `ALLOWED["ui"]`，而是把编排下移到 `app`
（`app` 本来就允许依赖 `tts`，`app/voice_call.py` 已经在用 `jarvis.tts.cloud`）。
判断依据很简单：**桌面壳是画界面的地方，网络调用不该长在那里。**

现在的分工是一条清晰的线，两边各有测试：

| 谁 | 知道什么 | 不知道什么 |
|---|---|---|
| `jarvis.app.voice_library` | 目录、索引、WAV | 网络、`tts` 包、厂商 |
| `jarvis.tts.cloud` | HTTP、base64、厂商字段名 | 索引、文件、哪个音色被选中 |
| `jarvis.app.voice_cloud` | 两者的**调用顺序** | 界面、桥面 |

`tests/test_architecture_layers.py::test_the_voice_store_does_not_reach_for_the_network`
钉住第一行（用导入图判定，不是搜文本——那个模块的 docstring 里就写着
`jarvis.tts.cloud`）。

## 桌面也能录了：录在 Python 进程里（2026-10-05，第 39 轮）

手机是页面 `getUserMedia` → base64 过 LAN → `voice_clone_add`。**桌面照抄会出事**：
这台机器的麦克风归 Python 的 ASR 环（听唤醒词那一圈），页面再开一路要么被设备拒，
要么"静默共享"把唤醒词的音频抢走——表现是**她突然听不见我说话了**，日志里什么都没有。

所以桌面的录音在进程内完成（`jarvis/app/voice_sample.py`），**音频一次都没过桥**：桥上来回
只有状态、名字、和"你刚才念的是哪一句"。三态 `idle → recording → captured`，页面 200 ms
轮一次——桥方法绝不能阻塞十几秒，那会冻住调用它的窗口。

录之前先问 `mic_busy`（= `VoiceService.capturing`），四条不合格**当场说出口**：
静音（峰值 `< 400` ≈ -38 dBFS）、太短（`< 2000 ms`，抄仓库的数）、到顶
（30 s = `min(仓库 MAX_MS, 30_000)`，到顶**自己收尾**，不然界面永远数着还没按钮）、
只有一个 take（`captured` 时再点开始录音被拒，上一段留着）。
**拒了不丢录音**：名字写错、句子没填、仓库报错，三种都只回一句话。

上传那一格和手机同一条规矩：**先存本机，再按勾选上传**，默认关；厂商失败只退成
"本地有 + 一句原因"。勾上时界面上直写"这段录音会离开这台机器"。

**但要说清本机还差什么**：`cloning_ready()` 在这台机器答 `True`，它只查文件。按上面
那张表，本地路径实际需要装得下 3.1 GB 显存的 GPU（模型加载那次实测 31.06 s / 3456 MiB，
CPU 回退 `0xC0000005`），而 `edge_tts` 不吃克隆 id。所以**没设 `DASHSCOPE_API_KEY` 时，
桌面录出来的音色能存、能选、能删，但还没法真的用你的声音回答**——勾上传（要 key）
是目前唯一走得通的一条。另一个已知不对称：`cloning_ready()` 只看文件，导致
"有 key、没装离线环境"的机器上桌面干脆不给录音入口，即使云端那条其实走得通。
细节与实测数字见 `docs/桌面运维手册.md` §11as。

## Key 放哪

`DASHSCOPE_API_KEY`。设置面板通过 `key_for="voice_cloud"` 写它
（`jarvis/app/settings_service.py::CLOUD_VOICE_PROVIDER`）。

**这个变量名在两处出现**：面板写的（`CLOUD_VOICE_KEY_ENV`）和客户端读的
（`jarvis.tts.cloud.DEFAULT_KEY_ENV`）。两处拼写一旦分叉，症状是
「我填了 key 但没反应」且**任何地方都不报错**，所以有测试直接断言两者相等
（`tests/test_app_settings_service.py`）。改任一处都要改另一处。

## 运维约束

1. **一次只跑一个 worker 实例。** 一台机器上多个 3 GB 级模型不可能共存，
   而且失败信息会指向"显存不足"而不是"你开了两个"。
2. **不要给 `_child_env` 加 `expandable_segments`。** Windows 不支持，静默忽略。
3. **一个 4 GB 卡上不要同时开桌面浏览器 + 离线语音。** 实测差 18 MiB 就崩。
4. **打包顺序永远是：先 `build_desktop`，再 PyInstaller。** 中间不要碰
   `jarvis/ui/web/`（见项目长期约定）。
