## 二、OPT-R111-1｜HUD 每一帧里有 50 毫秒在睡觉 【E，收益最大】

**实测。** `SystemMonitor.snapshot()` 一次 **68 毫秒**，拆开看：

| 读哪一项 | 耗时 | 占比 |
|---|---|---|
| **cpu** | **50.60 ms** | **75%** |
| net | 7.82 ms | 11% |
| procs | 5.42 ms | 8% |
| disks | 0.50 ms | 0.7% |
| memory | 0.13 ms | 0.2% |
| uptime | 0.00 ms | — |

那 50.6 毫秒**不是在算，是在睡**：`_read_cpu` 调的是
`psutil.cpu_percent(interval=CPU_SAMPLE_SECONDS, percpu=True)`，而 `CPU_SAMPLE_SECONDS = 0.05`
—— 这个调用会**在调用线程里 sleep 50 毫秒**，再拿前后两次 `cpu_times` 作差。

HUD 每 1.5 秒拉一次，于是这台机器**只要开着小夜，就永远有 3.4% 的一个核在那儿睡觉**
（50.6 ÷ 1500），而且是睡在 pywebview 线程池的线程上。

### 为什么不能简单改成 `interval=None`

因为那正是这个项目已经付过一次账的 bug。`CPU_SAMPLE_SECONDS` 的文档注释写得很清楚：
psutil 的 `cpu_percent(interval=None)` **按调用线程记基线**，而 HUD 由线程池服务，
没问过的新线程会答 0.0 —— 就是当初那条「CPU 一下 100% 一下 0%」。

本次重新实测，确认这条注释是真的：

```
C 验证 psutil 按线程记基线：
   线程 0  interval=None -> [0.0, 0.0, 0.0, 0.0]
   线程 1  interval=None -> [0.0, 0.0, 0.0, 0.0]
   线程 2  interval=None -> [0.0, 0.0, 0.0, 0.0]
   主线程（有基线）-> [23.8, 10.0, 30.0, 15.0]
```

`tests/test_monitor_refresh.py::TestTheMachineCpuRead` 就是钉这条的回归测试。

### 改法：基线自己拿，不借 psutil 那个按线程的全局

`psutil.cpu_times(percpu=True)` 是**无状态**的，谁调都一样，实测 **0.01 毫秒**
（比阻塞采样便宜 5000 倍）。所以把基线存在 monitor 实例上，自己作差：

- **第一次读**仍然走一次 50 毫秒阻塞采样 —— 保住「新建的 monitor 第一次读就是真读数，
  不是预热零」这条现有性质（`__main__.py` 的自检和 `insight_tools` 都依赖它）。
- **之后每一次**用 `cpu_times(percpu=True)` 对实例上的基线作差，**0 睡眠**。
  窗口从 50 毫秒变成真实轮询间隔（1.5 秒），读数更平、更有代表性。
- **基线太旧就重新预热**：机器睡过、窗口进过托盘、轮询停过，差分窗口会横跨整个空档，
  那个平均值虽然算得没错，但贴在「当前负载」那一格上就是在骗人。超过阈值就重新阻塞采样一次。

基线放在实例上而不是 psutil 的线程字典里，所以**哪个线程来问都是同一个答案** —— 这比原来
那条回归测试想钉的性质还要强一点。

**实测收益（已改完复量，详见 §九）**：`_read_cpu` **50.60 ms → 0.24 ms**，
稳态 `snapshot()` **68 ms → 17.18 ms**（中位数，−75%）。

**要动的**：`jarvis/tools/monitor.py`（`_read_cpu` 与常量），
`tests/test_monitor_refresh.py`（那条断言「每次 interval 都必须 > 0」的测试要改成钉**性质**：
① 第一次读是真读数 ② 换线程读不会变 0 ③ 第二次读不睡觉）。另外给 monitor 用的假 psutil
要补 `cpu_times`。

## 三、OPT-R111-2｜整个 ECharts 被打进包，只用了一条折线 【E】

**实测。** 打包产物 `jarvis/ui/web/assets/index-*.js` = **2,381,870 字节**，单一主分块。

`frontend/src/composables/useChart.ts` 第一行是 `import * as echarts from 'echarts'`
—— 这条路把**整个 ECharts** 拉进来：柱状、饼、雷达、地图、关系图、树图、桑基、K 线、仪表盘，
加 Canvas 和 SVG 两套渲染器。`echarts/dist/echarts.min.js` 本体就是 **1,096 KB**。

而全项目只有一处用图：`TrendPanel.vue` 的 CPU／内存双折线。它实际需要的是
**`LineChart` + `GridComponent` + `TooltipComponent` + `CanvasRenderer`**，就这四个。
图例是自己用 HTML 画的，没用 `LegendComponent`。

### 改法

换成 ECharts 自己的按需注册入口，`option` 一个字都不改：

```ts
import * as echarts from 'echarts/core'
import { LineChart } from 'echarts/charts'
import { GridComponent, TooltipComponent } from 'echarts/components'
import { CanvasRenderer } from 'echarts/renderers'
echarts.use([LineChart, GridComponent, TooltipComponent, CanvasRenderer])
```

**行为零变化**（同一个 `echarts.init`、同一份 option），只是没被用到的图表类型不再进包。

**要动的**：`frontend/src/composables/useChart.ts`（改 import），
`frontend/src/components/TrendPanel.vue`（`EChartsOption` 类型改从 `echarts/types` 取）。

**实测收益（已改完复量，详见 §九）**：主分块 **2,381,870 → 1,753,443 字节**，
少 **628,427 字节（−26.4%）**。这份文档里写的是实际量出来的数，不是估的。

## 四、OPT-R111-3｜趋势图每 1.5 秒把整棵 option 深走一遍 【S】

`TrendPanel.vue` 结尾：

```ts
watch(option, (next) => chart.value?.setOption(next), { deep: true })
```

`option` 是 `computed`，每次重算都**返回一个新对象**，所以 watcher 靠对象身份变化就会触发
—— `deep: true` 在这里一点作用都没有，净开销：Vue 要把整棵 option 深度遍历一次收集依赖，
而那棵树里挂着两条各 60 个点的数组、十几层嵌套的样式对象。每 1.5 秒一次，白走。

而且那些依赖 computed 自己已经收齐了（它读的就是 `store.cpuHistory`／`memoryHistory`），
去掉 `deep` 不会少触发。

**改法**：删掉 `{ deep: true }`。

**要动的**：`frontend/src/components/TrendPanel.vue` 一行。

**诚实说明**：这条没有单独计时 —— 一次深遍历在 1.5 秒预算里量不出来，它属于
「白做的功，删掉没有代价」那一类，不是「实测省了 N 毫秒」。

## 五、OPT-R111-4｜没人打开的宠物弹窗，每次启动都去读一遍图 【E 代码事实】

`frontend/src/components/PetForgePopup.vue` 最后一行：

```ts
onMounted(() => void load())
```

**没有判 `props.open`。** 而 `App.vue` 里这些弹窗是无条件挂载的（靠 `:open` 控制显示），
所以这一句在**每次启动**都会跑，给一个关着的对话框拉数据。

`load()` 走 `pet_assets()` → `PetService.assets()`，那一路会：

- `self._library.figures()` 逐个 `to_public()`，而 `to_public()` 里有
  `"preview": _read_preview(self.preview_path)` —— **每一行都读一个 PNG 再 base64**，
  上限 `MAX_FIGURES = 12`；
- `weights_gap()` 去盘上看分割模型权重在不在；
- `pet_gallery.models()` 枚举随包模型。

对比：隔壁 `ExtensionsPopup.vue` 是**判了**的（`onMounted(() => { if (props.open) void load() })`）。
所以这不是设计，是漏了一个判断。

**诚实说明**：全新装的机器宠物库是空的，这一下几乎不花钱。**代价随用户生成过的宠物数量涨**，
满 12 个就是 12 次 PNG 读 + base64 + 一个不小的 JSON 过桥 —— 全为了一个没打开的对话框。
本机当前宠物库的真实条数没查（那是用户数据目录，不去翻），所以这条的收益我**不给毫秒数**。

**改法**：和 `ExtensionsPopup` 对齐，挂载时判 `props.open`。`watch(props.open)` 那条已经在了，
打开的时候照样会拉。

## 七、明确不做的事

| 不做 | 为什么 |
|---|---|
| **把 Python 导入拆成懒加载** | `import jarvis.ui.desktop` 实测 450 ms，最大一块是 `jarvis.llm.transport` 的 `urllib.request`（105 ms）。双击到出窗实测约 2 秒，拆完省不到 0.1 秒，代价是在网络主路径上加分支 —— 不划算 |
| **给磁盘读数加 TTL** | 本机实测 `disk_partitions` 0.6 ms + 三个盘 `disk_usage` 合计 0.45 ms。有网络映射盘或空光驱的机器上可能卡住（**S，本机没复现**），但为一个没量到的问题改一条每帧都走的路，不如留着 |
| **把 3D 人物（three + three-vrm）改成异步加载** | 包里确实压着 `three.core` 1424 KB + `three-vrm` 965 KB（未压缩源码）。但 `AvatarStage` 是默认就显示的主体，改成异步会让 HUD 先出、人物后补 —— 那是**看得见的行为变化**，得你点头，我不替你定 |
| **把 12 个弹窗全改成按需挂载** | 收益真实（九个弹窗约 9300 行 Vue 能挪出启动路径），但要逐个确认「关着的时候它不做事」。这一窗为 z-index 和文档顺序付过两次账，一次动十二个组件风险不成比例 —— 单独排一轮 |
| **把随包的四份 GGUF 减成一份** | 包 10.3 GB 里 9.87 GB 是四份模型（7B 4.68 + 4B 2.72 + 1.7B 1.83 + 0.6B 0.64）。这是**卖法的决定不是技术问题**：发货清单、买家说明书、界面上那个「选哪个离线模型」都按四份写的。要减得你说减 |

## 九、实施记录（改完实测）

五条全做了。下面每个数字都是本机当场量的，命令和脚本留在 `reports/`。

### 1. CPU 读数：`_read_cpu` 50.60 ms → 0.24 ms

同一台机器、同一个默认配置的 `SystemMonitor`（所以 `procs` 也在账里，和 §二 那张 68 ms 的表对得上），
稳态下每 1.5 秒一帧、取 8 帧（`reports/measure_r111.py`）：

| | 改前 | 改后 |
|---|---|---|
| 稳态 `snapshot()` | **68 ms** | **17.18 ms**（中位数；8 帧 15.86–26.48） |
| 其中 cpu | **50.60 ms** | **0.24 ms** |

改后稳态的开销排序变了，CPU 从第一名掉到倒数第二：

```
net     8.01 ms      ← 现在的大头
procs   6.07 ms
disks   1.10 ms
memory  0.77 ms
cpu     0.24 ms      ← 改前是 50.60
uptime  0.01 ms
```

**表针没动。** 这条改动唯一的风险是"换了便宜的路，读数就不准了"，所以单独对了一遍
（`reports/verify_r111_cpu.py`）：同一个 1.5 秒窗口里，小夜差分 `cpu_times` 得到的整机占用
和 psutil 自己的 `cpu_percent` 相差 **0.1–0.3 个百分点**（第一帧差 1.9，是两边基线起点差了
几十毫秒，之后washout）。逐核读数在真节奏下是正常的散开（12.1% 整机 / 4.2–22.9% 逐核）。

**当初那条 bug 不复现。** 三个全新线程各自问同一个 monitor，读到 26.4 / 22.5 / 15.1 —— 没有一个
0.0。改之前 `interval=None` 在新线程上必答 0.0，这正是「CPU 一下 100% 一下 0%」的现场。
新性质比原来那条回归测试想钉的还强一点：**哪个线程来问都是同一个答案**。

### 2. 第一帧 572 ms 不是这条改动的账

要先说清楚，免得以后有人拿这个数来翻案：第一帧实测 **572.46 ms**，但把它各项单独再量一遍
只有 67 ms 左右。差额是 **psutil 进程内第一次 `virtual_memory()` 的一次性开销**（上一轮量到
514.29 ms）—— 同一个进程里新建第二个 monitor 再量，memory 只要 0.93 ms，因为那笔钱第一帧
已经付过了。这是 psutil 的进程级初始化，和 CPU 采样无关，也不是这一轮能改的。
第一帧里属于 CPU 的那 50.84 ms 是**故意留的**：新建的 monitor 第一次读必须是真读数。
