## 2. 方案

每项都写：动机 / **证据** / 接口 / **爆炸半径** / 代价 / 验收判据。

### 2.1 修：通过开关打开的宠物收不到语音状态

- **动机**：宠物页的「聆听中 / 思考中」姿态读的是 `window.__jarvisState` 推过去的
  `voice.turn/phase`。而那个推送只发给 `window_box` 里的窗口。
- **证据**：`_deliver`（`jarvis/ui/desktop.py:1924`）只遍历 `window_box`；而
  `window_box.append(created)` **全仓只出现在一处**——`_restore_pet_on_load`
  （`jarvis/ui/desktop.py:1840`），也就是"上次退出时宠物开着"的启动恢复路径。
  另一条路径 `pet_toggle`（`jarvis/ui/desktop.py:426`）→ `lifecycle.toggle_pet()`
  （`jarvis/ui/lifecycle.py:455-463`）只调 `pet.toggle()`，**不登记窗口**。
- **影响**：用托盘菜单或 HUD「宠物」按钮打开的宠物，**收不到任何状态推送** →
  她不会显示聆听/思考姿态，情绪永远停在初始态。
  而气泡（`pet.on_snapshot`，`jarvis/ui/pet.py:699`）是**直连** state 的，照常工作——
  所以症状是"她能说话、气泡也出，就是姿态永远不动"，这反而把问题盖住了。
- **接口**：`PetController` 加一个 `on_window_change` 回调（显示成功 / 隐藏时各通知一次），
  shell 侧统一负责登记与移除。把"窗口登记"从**某一条路径的一次性动作**改成
  **控制器的固有行为**，这样以后再加第三条显示路径也不会漏。
- **爆炸半径**：`jarvis/ui/pet.py` 一个回调 + `jarvis/ui/desktop.py` 装配处几行。
  不改 `_deliver` 的语义，不改前端。
- **代价**：无（回调在显示/隐藏时各触发一次）。
- **验收**：测试证明 ① `pet_toggle()` 之后 `window_box` 里出现宠物窗口；
  ② `hide()` 之后它被移除（否则死窗口会一直被推）。

### 2.2 修：单实例门站得比服务启动还晚

- **动机**：托盘模式下"双击第二次"是操作者的**预期动作**（他找不到窗口就会再点一次）。
  第二个进程必须什么都不做就退出。
- **证据**：`jarvis/__main__.py:790` 先跑 `app.start()`（`jarvis/application.py:102-126`
  会启动 scheduler / workflow、打开数据库、把持久任务重新挂上），
  之后才在 `desktop.run` 内部 `jarvis/ui/desktop.py:1481` 调 `gate.claim()`。
- **影响**：第二次双击时，新进程在退出前**已经开了第二个 SQLite 连接，
  并让第二个调度器注册了持久任务**。`misfire_grace_seconds=60` 意味着刚过期的任务
  会被立刻补跑 → **提醒重复响、工作流重复执行副作用**。这正好是 2.1 之外
  另一条"偶发重复"的来源。
- **接口**：把 `claim()` 提到 `app.start()` **之前**。`desktop.run` 保留 gate 参数
  作为兜底（测试直接调 `run()` 时仍然要能拦住），但主路径由 `__main__` 先占坑。
- **爆炸半径**：`jarvis/__main__.py` 的启动顺序 + `jarvis/ui/desktop.py` 的
  gate 复用（`InstanceGate` 已支持重复 claim 幂等？需要核实并处理）。
- **代价**：一次文件锁尝试，比现在更早，更快失败。
- **验收**：测试证明"第二个实例在 `app.start()` 之前就被拦住"，
  且**第一个实例的服务只启动过一次**。

### 2.3 修：工作流删掉之后，调度表里的陈旧 job 会永久失败

- **动机**：工作流的 cron 触发是"往调度器里注册一条 job"实现的。注册要跟着定义走。
- **证据**：`_sync_schedule`（`jarvis/workflow/service.py:337-367`）**只 `add_job`、
  没有 `remove_job`**；`reload()`（`jarvis/workflow/service.py:126`）走同一条路。
- **影响**：删掉一个工作流定义、改了名字、或者把 trigger 从 `cron` 改成 `manual`
  之后，`scheduler_jobs` 里的旧行**仍然在**。到点触发 →
  `run(name)` 找不到定义 → 抛 `工作流不存在` → 每次都进失败计数，**永久失败**。
  这是"我改了配置，它却一直在报错"的经典来源，而且用户看不出来源在哪。
- **接口**：`_sync_schedule` 改成 **diff**：先算出"应该存在的 job_id 集合"
  （`workflow:` 前缀 + 当前定义里所有 cron 型），再把库里带 `workflow:` 前缀、
  但**不在集合里**的 job 删掉。`reload()` 复用同一条路。
- **爆炸半径**：`jarvis/workflow/service.py` 一个方法。**只删自己命名空间下的 job**
  （`workflow:` 前缀），绝不碰 `reminder:` 和别的组件的 job。
- **代价**：每次同步多一次 `list_jobs()` + 少量 `remove_job`。
- **验收**：测试证明 ① 删掉定义后 job 从调度表消失；
  ② trigger 从 cron 改成 manual 后 job 消失；
  ③ **`reminder:` 前缀的 job 一个都没被碰**。

### 2.4 修：一条死窗口会拖慢整批状态推送

- **动机**：状态快照要同时发给 HUD 和宠物两个窗口。
- **证据**：`_deliver`（`jarvis/ui/desktop.py:1934`）的循环**没有逐窗 try**。
- **影响**：一个僵死窗口抛异常 → 整批推送中断 → 后面的窗口收不到 →
  状态泵进入退避限速（`jarvis/ui/pump.py:140-146`）→ HUD 的实时状态一起被拖慢。
  一个窗口的问题不该变成所有窗口的问题。
- **接口**：逐窗 try/except；抛异常的窗口**从 `window_box` 移除**
  （已经推不进去的窗口，留着只会每轮再失败一次），并记一条 warning。
- **爆炸半径**：`jarvis/ui/desktop.py` 一个函数。
- **代价**：无。
- **验收**：测试证明"第一个窗口抛异常时，第二个窗口仍然收到快照"，
  且坏窗口被移出列表。

### 2.5 扩展：自动化面板（把三块后端能力接到眼睛上）

- **动机**：见 §1 那条——`scheduler` / `workflow` / `planner` 三块后端能力
  在桌面端**零入口**，而 `stats()` 的 docstring 明确写着它们是给这个面板准备的。
  现在的情况是：调度器在跑、工作流有定义、规划器能出计划，**用户既看不见也管不着**。
- **接口**：`AssistantPopup` 加第四个页签「自动化」，三块：
  1. **定时任务** —— 表格：名称 / 触发器 / 下次运行 / 启用态 / 最近一次结果。
     操作：启停、手动试跑、删除。
     数据：`scheduler.list_jobs()` + `next_run_time(id)` + `history(id, limit=1)`。
     **过滤掉 `reminder:` 前缀**——提醒归「提醒」页签管，两个入口管同一批 job 迟早打架。
  2. **工作流** —— 定义表（名字 / 触发器 / 步骤数 / 来源文件）+ 最近运行历史。
     操作：手动跑一次、重新读取定义（`reload()`，这样新加的 YAML 不用重启）。
     数据：`workflow.definitions()` + `workflow.history(limit)` + `stats()`。
  3. **计划** —— 给一个目标，出计划。数据：`planner.plan(goal)`。
- **桥面方法**（9 个）：`automation_overview` / `scheduled_jobs` / `job_toggle` /
  `job_run` / `job_remove` / `workflow_definitions` / `workflow_run` /
  `workflow_reload` / `plan_goal`。
- **两条必须写进界面的边界**（这是这轮最重要的一行字）：
  - **`planner` 只出计划，不执行**。面板上要写死这句话——能力清单里它本来就标着
    「只出计划、没有接执行」，界面上不能让它看起来像"按一下就替你做完"。
  - **工作流跑起来之后，每一步照旧吃各自的开关**。手动跑一个工作流**不是**绕过
    安全策略的后门：里面的 `run_shell` 该被档位拦还是被拦。面板文案要说清这件事，
    否则用户会以为"点这个按钮等于全权限"。
- **命名空间守卫**：`job_toggle` / `job_run` / `job_remove` 三个方法**拒绝
  `reminder:` 前缀的 job**，返回"请到「提醒」页签操作"。理由同上：同一批数据
  两个入口，必须有一个人说了算。
- **爆炸半径**：`desktop.run` +3 个可选参数（缺省 `None` 时对应页签显示"这个进程没接"，
  与现有 `memory`/`knowledge` 的处理方式一致）、`HudBridge` +9 方法、
  `__main__.py` 传参、前端一个页签。**不改任何后端服务的语义**——面板只调用它们
  已有的公开方法。
- **代价**：无轮询（页签打开时才读），与 `AssistantPopup` 现有三个页签同一条规矩。
  `plan_goal` 会**调一次大模型**（计费），界面上要说明。
- **验收**：① 桥面 9 个方法各有测试（用假服务，覆盖"服务缺失"与"服务抛异常"
  两条失败路径）；② 页签能列出真实数据、启停与删除生效；
  ③ `reminder:` 前缀被三个操作方法拒绝。

### 2.6 长期运行：运行历史表没有保留策略

- **动机**：桌面端是要常驻的（开机自启已经在上一轮做了）。
- **证据**：`scheduler_runs`（`jarvis/scheduler/store.py:58-71`）与
  `workflow_runs`（`jarvis/workflow/store.py:34-47`）**只 append**；
  全仓没有 `DELETE FROM *_runs`。而 `count_runs`（`jarvis/scheduler/service.py:308-309`）
  每次都是全表 `COUNT(*)`。
- **影响**：WAL 模式下这两个表会随运行时间单调增长；计数查询的代价跟着涨。
  能力清单里"7×24 常驻稳定性未验证"——这是其中一条能**提前拆掉**的地雷，
  不用等一次长时间运行测试才发现。
- **接口**：store 加 `prune(keep=N)`；service 在 `start()` 时调一次。
  保留最近 N 条（N 取一个足够大的常数，够看历史、不会无限长）。
- **爆炸半径**：两个 store + 两个 service 的 `start()`。**不动表结构**，不写 migration。
- **代价**：启动时一次 `DELETE`。
- **验收**：测试证明"插入超过上限后，启动会把最旧的删掉、最近的还在"。

### 2.7 性能：宠物轮询每轮取两次光标

- **证据**：`_push_pointer`（`jarvis/ui/pet.py:724`）与 `_sync_to_cursor`
  （`jarvis/ui/pet.py:791`）**各调一次 `_cursor_position()`**，而
  `_sync_to_cursor` 又调用 `_push_pointer` → 一轮里取两次；轮询是 20 Hz
  （`jarvis/ui/pet.py:92,748-752`），等于约 40 次系统调用/秒做同一件事。
- **接口**：`_poll_once` 采样一次，往下传。
- **爆炸半径**：`jarvis/ui/pet.py` 三个方法签名。
- **代价**：无（只减不增）。
- **验收**：测试用计数器证明"一轮只取一次"。

### 3.2 打包卡死五小时的真凶（这一轮最大的意外）

打包在 `INFO: Looking for dynamic libraries` 之后**永久停住，日志不再增长，没有任何错误**。
对照 `build-r27.log`，这一步本来只要 **78 秒** —— 这是判断"到底卡了还是就是慢"的唯一客观依据。

用 `py-spy dump` 抓栈（装它只要几秒，是唯一能给出答案的工具）：

```
find_binary_dependencies → isolated._parent.call        （主进程在等子进程）
  └─ modelscope/ops/ailut/pyinterfaces.py:13
     └─ torch.utils.cpp_extension.load()
        └─ torch/utils/file_baton.py:50  wait()          （子进程在等一个文件锁）
```

**两层原因叠在一起**：

1. `modelscope.ops.ailut` 在 **import 时**就调 `torch.utils.cpp_extension.load()`，
   要现场编译 CUDA 扩展 —— 而构建机**既没有 nvcc 也没有 ninja**。
2. `torch` 用**文件锁**串行化编译。**一次被 kill 的编译会留下 0 字节的锁文件**，
   此后**所有** import 都永久阻塞在 `wait()` 上。锁在
   `%LOCALAPPDATA%\torch_extensions\...\cudaops_ailut\lock`，实测时间戳正是第一次打包后一分钟。

**为什么 PyInstaller 会去 import 它**：`build_main.py:965-967`
`find_binary_dependencies(self.binaries, self.graph.get_collected_packages(), ...)`
—— 它把**模块图里的每一个包**都 import 一遍，为的是捕获 import 期间对
`os.add_dll_directory` / `PATH` 的修改。所以只要这个模块在图里，打包就必挂。

**解法（三处一起）**：删掉陈旧锁；spec 里 `collect_submodules("modelscope", filter=...)`
把它挡在 hiddenimports 外；同文件 `Analysis(excludes=[..., "modelscope.ops.ailut"])`
把它踢出模块图。**验证**：清锁后 import 从"90 秒超时"变成"1 秒内抛 `RuntimeError: Ninja is required`"；
收集从挂死变成 **13 秒 / 407 个模块**；打包 **14.2 分钟**完成。

**排除它的依据**：`grep -rn "ailut" jarvis/` **零命中**，项目里 `modelscope` 只出现在环境变量名

### 3.4 两条环境限制（本轮踩实了，已进 MEMORY.md）

1. **Bash 调用一结束，它启动的后台进程就被清理**。所以"启动 exe、下一次调用再去看"
   永远看不到活着的窗口 —— 启动、截图、点击必须**在同一次调用里**完成。
   这是"进程血统影响 GUI 行为"那条已知限制的具体长相。
2. **两个 pytest 进程不能共用 `--basetemp`**（会互删临时目录，踩过一次 739 个 setup 失败）；
   **批量删除被拦**导致全量测试里有 20–30 个 `SystemExit`（数量波动），
   判断回归的方法是看失败原因是否清一色 `SystemExit`。

### 3.1 执行中撞到的两件事（都值得记）

1. **`InstanceGate.claim()` 不幂等**（2.2 的前置缺陷）。原实现的第二次 `claim()` 会重新 bind、重写锁，
   而锁里的端口指向一个**从来没人监听**的 socket —— `start()` 只在赢家侧调用一次。
   也就是说：如果不先修它，"把 claim 提前到 `app.start()` 之前"这个改动会让
   **每一次后续双击都叫不醒第一份实例**，然后新进程照旧开第二份。这是"修一个 bug 要先修它脚下的 bug"。
2. **全量测试里的 31 个 `SystemExit: 1` 不是回归**。这个执行环境拦截批量删除，
   任何"真的删文件/目录"的测试都会以退出码 1 结束。两条证据：全部 31 个失败的
   原因**都是** `SystemExit: 1`（一条断言失败都没有）；受影响的模块单独跑 314 项全绿。
   基线在同一环境里是 2013 条 / 23 个同类，说明这类失败的数量会随运行波动。

   顺带记一条自己的操作教训：**两个 pytest 进程不能共用同一个 `--basetemp`**。
   我第一次把全量测试和单文件测试并发跑，它们互相删掉了对方的临时目录，
   于是出现 739 个 `failed on setup` —— 看上去像大规模回归，实际是自己踩了自己。
