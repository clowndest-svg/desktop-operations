> 状态:✅ 完成 | 日期:2026-07-29 | 门禁:Ruff / Black / MyPy strict / pytest 全绿

## 1. 交付内容

### 1.1 `jarvis/logging` 包(L1,新增)

| 模块 | 职责 |
|---|---|
| `formats.py` | 统一日志布局 `LOG_FORMAT` + `StructuredFormatter` + `metrics()` 结构化字段构造器 |
| `service.py` | `LoggingService` 生命周期组件(handlers/级别/excepthook 的安装与还原) |

> 命名说明:包名与标准库 `logging` 同名。Python 3 绝对导入下无歧义——包内 `import logging`
> 永远解析到标准库,外部以 `jarvis.logging` 引用本包。

### 1.2 双通道输出

- **控制台**(`logging.console`):stderr,便于与程序 stdout 输出分离
- **滚动文件**(`logging.file_enabled`):`<data>/logs/jarvis.log`,按 `max_bytes` 滚动、保留 `backup_count` 份,UTF-8

### 1.3 结构化记账字段(规格第十五章基础)

```python
logger.info("reply ok", extra=metrics(latency_ms=843.2, tokens_in=512, tokens_out=128, cost_usd=0.00094))
# ... | jarvis.llm | reply ok | latency_ms=843.2 tokens_in=512 tokens_out=128 cost_usd=0.000940
```

不发明并行日志 API:沿用标准 `extra=` 机制,`StructuredFormatter` 渲染为稳定的
`key=value` 后缀(顺序固定、可机器解析)。无指标的记录与普通日志完全一致。
阶段五起 LLM 层的 token/延迟/成本统计直接复用。

### 1.4 第三方降噪(结构化方案,零名单)

不维护脆弱的"吵闹库名单",利用 logger 层级结构:

- **root** 级别 = `logging.third_party_level`(默认 `WARNING`)→ 所有第三方日志被钳制
- **`jarvis`** 命名空间级别 = `logging.level`(默认 `INFO`)→ 第一方日志按配置放行

由此产生一条**架构纪律**(已写入 架构分层.md):第一方 logger 名必须以 `jarvis.` 开头,否则会被当第三方降噪。

### 1.5 未捕获异常统一出口

`sys.excepthook` 接管:任何未捕获异常以 CRITICAL 级别记录**完整堆栈**(进文件+控制台)后进程退出;
`KeyboardInterrupt` 例外——用户 Ctrl+C 不是崩溃,委托回原钩子保持默认行为。`stop()` 时还原原钩子。

### 1.6 生命周期与接线

- `LoggingService(settings_provider)` 采用**延迟求值**:注册时配置尚不存在,`start()` 时才向
  `ConfigService` 取快照(组件按注册顺序启动,天然满足时序)
- `start()` 保存 root handlers/级别/excepthook → 撤下 bootstrap handlers → 安装正式配置;
  `stop()` 逐项还原并关闭自有 handlers,幂等且永不抛出
- `__main__`:bootstrap logging 只存活到 `LoggingService.start()`;`-v` 优先于配置强制 DEBUG
  (通过 `dataclasses.replace` 生成覆盖快照,不破坏不可变性)

### 1.7 配置新增键

`logging.third_party_level`(默认 `WARNING`,合法值同 `level`),defaults.yaml 已文档化。
